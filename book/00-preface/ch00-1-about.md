# 0.1 这本书是什么，给谁

> 基准：pi `b79e4cc8` (v0.84.4)　·　[版本表](../../research/BASELINE.md)　·　[参与指南](../../CONTRIBUTING.md)

## 为什么写这本书

pi 自带的手册有 718 行，写得不差。它告诉你 API 怎么调、扩展怎么装。

它不会告诉你三件事：

**第一，为什么这么设计。** pi 明确不做权限系统、不做沙箱、不做 MCP、不做 subagent、不做 plan mode。这些不是"还没做"，是**论证过之后决定不做**。最锋利的一句写在 `packages/coding-agent/docs/security.md:35`：一个半吊子的进程内沙箱"很容易被误解为一道安全边界"——所以宁可不给。理解这一批"不做"，比理解"做了什么"更重要，因为它直接决定了你要补什么。

**第二，边界在哪。** pi 的立场是「提供机制，不提供策略」。这句话翻译成工程语言：每一个拿 pi 做产品的团队，都得自己补齐同一批东西——权限、隔离、循环保护、遥测、凭据边界。pi 给你钩子，策略是你的事。这本书把那批东西列清楚，并给出最小实现。

**第三，别人已经怎么做了。**

## 第三点是这本书最独有的部分

阶跃星辰、MiniMax、月之暗面三家的 Code Agent **代码衍生自 pi**（衍生程度从"整树硬拷贝"到"只 vendor TUI"，差别很大，见 [血缘图谱](../../research/BASELINE.md#血缘谁和-pi-是什么关系)）。

DeepSeek 与智谱则是**自研内核**——它们在没有 pi 的前提下，独立面对了完全相同的那批问题。

所以手里的材料是：**同一个基座、三支衍生团队、两个独立对照组，五套全都交付给了真实用户的答案。**

这比"四家都用 pi"更有用，原因在对照组。看三家衍生方时，你永远分不清一个设计是他们的判断还是 pi 的路径依赖——因为他们共享上游。对照组正好切断这条线：

> 当三家衍生方做法趋同，而两个自研方也做了同样的事 —— 这就是这个问题的标准解，你照抄不会错。
>
> 当三家趋同，但两个自研方走了别的路 —— 那是 pi 的路径依赖，你有得选。

两个对照组的角度还不一样。`deepseek-harness` 走到了插件化的另一个极端（Cordis DI 容器上 315 个包，`compaction`/`context`/`spill`/`guard`/`subagent` 各自成包），是对 pi「794 行内核 + 6 万行单体产品层」的正面反例；`ZCode` 则是与 pi 完全无交集的独立演化。

> ⚠️ 一处容易搞错的地方：`deepseek-harness` 里确实存在 `@earendil-works/pi-ai` 依赖，但它挂在一个**默认休眠的可选第三方 provider 适配器**上，不在 DeepSeek 自家的模型路径上。证据与行号见 [`research/deepseek-harness/README.md`](../../research/deepseek-harness/README.md)。**把它算成"用 pi 的厂商"会让整个对照实验失效。**

这份对照实验本书讲两遍：

- **第三部分按问题横切** —— 一章一个策略问题，看各家各自怎么答，对照组单独标出；
- **第六部分按厂商纵切** —— 一章一家，看它的完整 diff 和内部一致性。

同一份材料，两条检索路径。你解决具体问题时走第三部分，你想看一家的整体判断时走第六部分。

## 不做什么

**不做评价性排名。** 本书写「kimi 把 subagent 放进了进程内，代价是一次扩展崩溃会带倒主循环」，不写「kimi 的做法比 minimax 更好」。

两个原因。一是读者需要的是判断依据，不是结论——你的约束条件和他们不一样。二是**各家面对的约束我们并不完全知道**：产品形态、团队规模、交付时间都会影响选择，而这些从代码里看不出来。

**不做 pi 的 API 手册。** 官方手册已经有了，本书只在它不够用的地方补（比如第 9 章的「任务 → API 反查表」，因为官方是按 API 组织的，你查的时候是按任务查的）。

**不谈 Claude Code 的内核实现。** 它是闭源的，本书引用的任何东西都来自公开文档或开源的插件层。

## 一条纪律

本书每一处 `file.ts:123` 都指向 [`research/`](../../research/) 里锁定 commit 的研究底稿，**不指向任何仓库的当前 HEAD**。

pi 每月 400–530 次提交。指向 `main` 的行号三周就会指到别的代码上。代价是这本书会落后于上游；收益是**每一条都能被复现**——你 checkout 同一个 commit，看到的就是同一段代码。

对一本讲工程判断的书，可复现比时效重要。

## 事实与推断分开写

沿用研究底稿的做法：

> 【代码事实】`agent-loop.ts:252` 的 `shouldStopAfterTurn` 在 `packages/coding-agent/src/` 中零调用点。
>
> 【推断】这更像是遗漏而非设计——相邻的 `uncaughtException` 路径被仔细处理过。

你要能随时判断哪些是可验证的、哪些是作者的判断。
